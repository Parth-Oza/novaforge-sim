# NovaForge Sim Architecture

## Design goal

NovaForge separates deterministic world evolution from presentation. A scenario should produce the same state history when given the same seed and fixed-step sequence, whether it runs in the browser, a test, or a future remote worker.

## Core modules

### Scenario model

`src/sim/types.ts` defines the public data contract for robots, obstacles, sensors, and snapshots. `schema/scenario.schema.json` provides the matching authoring contract for JSON scenarios.

### Simulation engine

`src/sim/engine.ts` owns simulation time, dynamic obstacle motion, robot kinematics, replanning, sensor updates, and metrics. It publishes structured-clone-safe snapshots and does not render.

### Planner

`src/sim/planner.ts` contains grid-based A* with eight-connected motion, diagonal corner protection, obstacle inflation, and line-of-sight path simplification.

### Sensor models

`src/sim/lidar.ts` implements configurable two-dimensional LiDAR ray casting against world boundaries and axis-aligned obstacles. Gaussian noise is generated by the seeded random source.

### Interface

React components consume snapshots. `SimulatorCanvas` renders the digital-twin view, while control and telemetry components remain ordinary accessible HTML.

### Batch runner

`src/cli/batch.ts` runs repeated seeded scenarios without a browser. It applies the same
acceptance evaluator as the interface and exits non-zero when any run fails, making scenario
evidence directly usable in CI.

### Acceptance evaluator

`src/sim/evaluation.ts` compares simulation metrics with the thresholds stored in each scenario.
It returns structured checks instead of a single opaque boolean, so the browser, batch reports,
and future ROS 2 integrations can explain exactly why a run passed or failed.

## Determinism contract

New modules must follow these rules:

1. Simulation state advances only through an explicit time step.
2. Randomness comes only from an injected seeded generator.
3. Rendering never changes simulation state.
4. Object iteration must not rely on unstable ordering.
5. Every deterministic guarantee has a repeatability test.

## Extension seams

Planned interfaces will allow contributors to register:

- Sensor models
- Global and local planners
- Robot controllers
- Metrics and acceptance rules
- Scenario generators
- Import and export adapters

The interfaces will remain data-oriented so implementations can eventually run in Web Workers, Node.js workers, or remote services.
