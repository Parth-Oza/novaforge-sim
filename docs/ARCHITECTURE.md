# NovaForge Sim Architecture

## Design goal

NovaForge separates deterministic world evolution from presentation. A scenario should produce the same state history when given the same seed and fixed-step sequence, whether it runs in the browser, a test, or a future remote worker.

## Core modules

### Scenario model

`src/sim/types.ts` defines the public data contract for robots, obstacles, sensors, and snapshots. `schema/scenario.schema.json` provides the matching authoring contract for JSON scenarios.

### Simulation engine

`src/sim/engine.ts` owns simulation time, dynamic obstacle motion, robot kinematics, replanning, sensor updates, and metrics. It publishes structured-clone-safe snapshots and does not render.

### Planner

`src/sim/planner.ts` defines the global-planner seam and two plugins:

- `astar`: the default grid-based A* behavior with eight-connected motion, diagonal corner protection, obstacle inflation, and line-of-sight path simplification;
- `direct-line`: a deliberately small example that succeeds only when the complete start-to-goal segment is clear.

The engine selects a plugin from `scenario.planner` and knows nothing about its algorithm. Missing configuration resolves to `astar`, preserving existing scenarios. A plugin receives a `PlannerRequest` and returns a `PlannerResult`:

```ts
type PlannerRequest = {
  start: Vec2;
  goal: Vec2;
  width: number;
  height: number;
  gridSize: number;
  obstacles: Obstacle[];
  padding: number;
};

type PlannerResult = {
  status: "found" | "blocked";
  path: Vec2[];
};
```

These contracts are data-only and structured-clone safe. A contributor adds an implementation to `plannerPlugins`, extends `PlannerId` and the JSON Schema enum, and writes deterministic tests without changing the engine. `planPath` remains as a compatibility wrapper around the default A* plugin.

### Sensor models

`src/sim/lidar.ts` implements configurable two-dimensional LiDAR ray casting against world boundaries and axis-aligned obstacles. Gaussian noise is generated by the seeded random source.

`src/sim/radar.ts` implements a deterministic two-dimensional radar abstraction for dynamic obstacles. Range and field-of-view checks use the obstacle center; output contains range, bearing relative to robot heading, and Cartesian obstacle velocity relative to the robot. Optional Gaussian noise for every reported quantity comes only from the injected `SeededRandom` instance. Obstacles are ordered by stable ID before noise is sampled, preventing input-array order from changing a replay.

The radar is intentionally a geometric autonomy-test sensor, not an electromagnetic propagation model. It does not model reflectivity, multipath, occlusion, Doppler ambiguity, or tracking. Scenarios opt in with:

```json
{
  "radar": {
    "maxRange": 260,
    "fieldOfViewDegrees": 120,
    "rangeNoiseStdDev": 0.8,
    "bearingNoiseStdDev": 0.006,
    "velocityNoiseStdDev": 0.12
  }
}
```

### Interface

React components consume snapshots. `SimulatorCanvas` renders the digital-twin view, while control and telemetry components remain ordinary accessible HTML.

### Batch runner

`src/cli/batch.ts` runs repeated seeded scenarios without a browser. It applies the same
acceptance evaluator as the interface and exits non-zero when any run fails, making scenario
evidence directly usable in CI.

### Acceptance evaluator

`src/sim/evaluation.ts` compares simulation metrics with the thresholds stored in each scenario.
It returns structured checks instead of a single opaque boolean, so the browser, batch reports,
and future ROS 2 integrations can explain exactly why a run passed or failed.

## Determinism contract

New modules must follow these rules:

1. Simulation state advances only through an explicit time step.
2. Randomness comes only from an injected seeded generator.
3. Rendering never changes simulation state.
4. Object iteration must not rely on unstable ordering.
5. Every deterministic guarantee has a repeatability test.

## Extension seams

Interfaces allow contributors to register or extend:

- Sensor models
- Global planners (implemented) and local planners (planned)
- Robot controllers
- Metrics and acceptance rules
- Scenario generators
- Import and export adapters

The interfaces will remain data-oriented so implementations can eventually run in Web Workers, Node.js workers, or remote services.
